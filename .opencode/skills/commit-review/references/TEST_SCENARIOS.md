# 测试场景

## 场景1: 正常提交流程

**前置条件**:
- 工作目录有未提交更改
- git已配置user.name和user.email

**操作步骤**:
1. 输入 `/commit-review`
2. 工具检查并显示改动文件
3. 输入提交信息: `feat(test): 添加测试功能#TB-1234#`
4. 确认格式验证通过
5. 查看AI评审结果（评分≥80）
6. 输入 `y` 确认提交
7. 查看提交成功提示

**预期结果**:
- 成功提交到当前分支
- 不生成、不修改、不暂存 commit_log.csv / commit_log.xlsx
- 评审证据保留在本次输出、agent runtime、MR 描述或 review notes 中
- 显示提交摘要

## 场景4: 多子模块处理

**前置条件**:
- 多个子模块有未提交更改
- 主项目也有更改

**操作步骤**:
1. 输入 `/commit-review`
2. 工具显示所有有改动的模块（包括子模块）
3. 输入提交信息
4. 阶段1：逐一评审所有模块（不提交）：
   - 获取diff
   - AI评审，记录评分和意见
5. 阶段2：汇总所有评审结果，统一判断
6. 阶段3：全部通过且用户确认后，统一提交所有模块

**预期结果**:
- 每个模块都经过评审
- 所有模块全部通过后统一提交，任一不通过则全部不提交
- 最终显示提交统计和 MR 链接

**前置条件**:

**操作步骤**:

2. 工具显示改动文件

   - cherry-pick到临时分支

   - 删除本地临时分支
   - 创建 temp_master={hash}
   - ...

**预期结果**:
- 主分支提交成功
- 临时分支创建并推送成功
- 本地临时分支已清理

## 场景6: cherry-pick冲突处理

**预期结果**:
- 冲突处理提示清晰
- 选择继续后可以正常解决冲突
- 解决后cherry-pick完成

## 场景7: 增强评审流程验证（复杂度路由 + LSP 上下文 + 结构化评分）

**前置条件**:
- 工作目录有未提交更改
- 改动涉及 2 个 Java 文件，共约 50 行
- AI 已加载 AGENT_WORKFLOW.md 中的增强评审流程

**操作步骤**:
1. 输入 `/commit-review`
2. 工具收集改动文件，计算复杂度：
   - 文件数：2 个
   - 改动行数：约 50 行
3. 路由决策：行数 ≤ 200 且 文件数 ≤ 5 → **标准评审**
4. AI 评审：
   - 输出 JSON 中间格式，包含所有必需字段
   - 应用评分矩阵计算分数
   - 逐项对照质量自检清单
5. JSON 输出检查：
   - 检查 `module` 字段存在
   - 检查 `findings` 数组非空
   - 检查 `score` 字段为 0-100
   - 检查 `score_breakdown` 包含计算过程
   - 检查 `verdict` 为"通过"或"不通过"
   - 检查 `summary` 为最终评审意见摘要
6. 最终输出格式检查：
   - 每条意见符合 `[标签]文件名:行号-描述` 格式
   - 标签属于 [缺陷]/[安全]/[兼容]/[性能]/[改进] 之一
7. 评分 ≥ 80 → 提交成功
8. 评分 < 80 → 拒绝提交并提示评审意见

**预期结果**:
- 复杂度路由：正确识别为标准评审（不是轻量，不是深度）
- JSON 输出：包含所有 6 个必需字段（module, findings, score, score_breakdown, verdict, summary）
- 评分矩阵：至少 1 个 finding 有扣分，显示计算过程（如 `100 - 10 = 90`）
- 质量清单：每条 finding 有文件名 + 行号，标签为 [缺陷]/[安全]/[兼容]/[性能]/[改进] 之一
- 评审证据：summary 格式为 `[标签]文件名:行号-描述`，可直接放入评审输出、agent runtime 或 MR 描述；不生成 CSV
- 通过 ≥ 80：提交成功
- 不通过 < 80：拒绝提交，显示评审意见
