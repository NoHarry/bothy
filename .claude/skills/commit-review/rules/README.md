# commit-review 规则框架说明

## 1. 项目规则目录约定

每个项目在项目仓库的根目录下创建自己的规则文件，存放于 `.review/rules/` 目录中。

**规则目录结构：**
```
{项目根目录}/
└── .review/
    └── rules/
        ├── android-java.md      # Android Java 项目规则
        ├── python-django.md     # Python Django 项目规则
        ├── node-express.md      # Node.js Express 项目规则
        └── ...                  # 其他项目类型规则
```

**重要说明：**
- `.review/rules/` 目录位于项目仓库内，**不是** SKILL 目录内
- SKILL 目录内的 `rules/` 目录仅存放框架规范和格式模板
- 各项目根据自身技术栈和编码规范，在 `.review/rules/` 下创建适合项目的规则文件

## 2. 规则优先级

| 优先级 | 来源 | 说明 |
|--------|------|------|
| 高 | 项目规则 (`.review/rules/*.md`) | 项目自定义规则，匹配时使用规则自身的扣分值 |
| 低 | 通用评审矩阵 | 当项目规则未匹配时，使用通用评分矩阵进行评审 |

**优先级规则：**
- 如果一条代码问题同时匹配项目规则和通用规则，**优先使用项目规则的扣分值**
- 项目规则应覆盖高频/高危问题，通用矩阵作为补充
- 扣分值可累加，但最高不超过 100 分（最低为 0 分）

## 3. 规则文件格式规范

每个规则文件必须包含以下结构，所有规则使用 **中文** 描述：

### 必要字段

| 字段 | 说明 | 示例 |
|------|------|------|
| 规则ID | 唯一标识符，格式 R-XX | R-01, R-02, R-03 |
| 严重级别 | 问题严重程度 | P0, P1, P2 |
| 检查项描述 | 问题的详细描述 | 空 catch 块未处理异常 |
| 正面示例 | 符合规范的代码 | 正确处理异常的代码 |
| 反面示例 | 不符合规范的代码 | 吞掉异常的代码 |
| 扣分值 | 扣减分数（整数） | -10, -15, -25 |

### 严重级别定义

| 级别 | 含义 | 典型扣分 |
|------|------|----------|
| P0 | 致命问题，可能导致系统崩溃或严重故障 | -20 ~ -30 |
| P1 | 严重问题，可能导致功能异常或安全隐患 | -10 ~ -15 |
| P2 | 一般问题，可能影响代码可维护性或性能 | -5 ~ -10 |

### 标签类型

每个规则必须使用以下 **5 个标签之一**：

| 标签 | 含义 | 适用场景 |
|------|------|----------|
| [缺陷] | 代码缺陷 | 空指针、数组越界、资源泄漏、逻辑错误 |
| [安全] | 安全隐患 | 硬编码密钥、SQL注入、权限校验缺失 |
| [兼容] | 兼容性问题 | API版本不兼容、多设备适配问题 |
| [性能] | 性能问题 | 主线程耗时、内存泄漏、冗余计算 |
| [改进] | 改进建议 | 代码优化、可维护性提升（不影响评分） |

## 4. 评审标签对照

| 评审维度 | 对应标签 | 说明 |
|----------|----------|------|
| 缺陷 | [缺陷] | 代码本身的错误或潜在错误 |
| 安全 | [安全] | 安全漏洞或风险 |
| 兼容 | [兼容] | 兼容性相关问题 |
| 性能 | [性能] | 性能相关问题 |
| 改进建议 | [改进] | 优化建议（不扣分） |

**标签使用规则：**
- 每条评审意见必须包含一个标签
- 标签必须放在意见最前面，格式：`[标签]内容`
- `[改进]` 标签不参与扣分，仅作为建议

## 5. 规则数量建议

| 项目类型 | 建议规则数量 | 说明 |
|----------|--------------|------|
| 小型项目 | 10-15 条 | 覆盖核心高频问题 |
| 中型项目 | 15-20 条 | 覆盖主要问题类型 |
| 大型项目 | 20 条以内 | 聚焦高危/高频问题，避免规则过于冗长 |

**建议：**
- 规则应聚焦**高频出现**和**高危**问题
- 避免创建过于细化的规则，增加维护成本
- 定期回顾和更新规则，适应项目演进
