# Skill: Code to Test

> 为已实现的代码创建完整测试套件。在 design-to-code 之后或任何需要补充测试覆盖的代码上使用。

## 何时使用
- 新代码已实现，需要编写测试
- 现有代码测试覆盖率不足
- 修复 bug 后，防止回归

## 前置条件
- 待测试的代码存在且能通过编译/通过 lint
- harness.yaml 中已配置测试框架
- 测试目录结构已建立

## 工作流程

### 步骤 1: 分析被测代码

对每个待测试的文件/模块：
- 阅读实现代码
- 识别公共 API（方法、函数、导出）
- 识别边界情况和错误路径
- 识别需要 mock/stub 的依赖
- 查看 harness/memory/domain-api-gotchas.md 了解已知的行为陷阱

### 步骤 2: 规划测试结构

- 将测试文件映射到源文件（1:1 或按模块分组）
- 遵循项目的测试命名约定
- 列出测试类别：
  - 正常路径测试（正常操作）
  - 边界情况测试（边界值、空输入、最大值）
  - 错误路径测试（无效输入、失败、异常）
  - 集成测试（如果组件有交互）

### 步骤 3: 检查现有测试桩

- 查找 design-to-code skill 创建的测试桩
- 以它们为起点
- 在桩的基础上补充缺失的测试用例

### 步骤 4: 实现测试

对每个测试文件：
1. 创建测试文件并导入所需模块
2. 设置测试 fixture/setup/teardown
3. 先实现正常路径测试
4. 实现边界情况测试
5. 实现错误路径测试
6. 添加描述性的测试名称和注释
7. 在测试文件上运行 lsp_diagnostics

### 步骤 5: 运行测试

1. 执行测试套件：`python scripts/validate.py --step test`
2. 如果测试失败：
   - 判断失败是在测试代码还是生产代码中
   - 如果是测试代码：修复测试
   - 如果是生产代码：记录 bug，最小化修复
3. 所有测试必须通过才能继续
4. 如果存在 `scripts/agent_runtime.py`，记录测试验证：
   ```bash
   python scripts/agent_runtime.py validation --command "python scripts/validate.py --step test" --status pass --summary "tests passed"
   ```

### 步骤 6: 检查覆盖率

如果配置了覆盖率工具：
- 运行覆盖率报告
- 识别未覆盖的路径
- 为显著未覆盖的代码补充测试
- 目标：在 harness.yaml 中配置（默认：80%）

### 步骤 7: 测试质量审查

自我审查测试的以下方面：
- 不测试实现细节（测试行为而非内部实现）
- 不存在不稳定测试（时间相关、顺序相关、外部服务调用）
- 每个测试只验证一个功能点
- 测试名称描述预期行为
- 正确的断言消息

### 步骤 8: 更新 BLACKBOARD

- 更新需求状态以反映测试完成情况
- 记录达到的覆盖率
- 关联 trace 条目

### 步骤 9: 编写 Trace 条目

创建 trace 条目，包含：
- 创建的测试（数量和文件列表）
- 达到的覆盖率
- 测试过程中发现的任何 bug
- 发现的任何新陷阱

如果是 bug 修复或重复失败补测试，同时在当前 runtime run 的 `eval-candidates.yaml` 中记录候选回归 eval；不要直接写入 `harness/evals/`，除非当前任务明确包含 owner review 后的 repo eval 提升。

### 步骤 10: 生成测试报告

产出简要测试摘要：
- 总测试数：N（通过：N，失败：0）
- 覆盖率：N%
- 已测试的文件：列表
- 已知缺口：列表（附说明）

## 完成标准
- [ ] 所有公共 API 都有测试
- [ ] 覆盖正常路径、边界情况和错误路径
- [ ] 所有测试通过
- [ ] 达到覆盖率目标（或缺口有合理解释）
- [ ] 不存在不稳定测试
- [ ] 重要 bug 修复已记录 runtime eval candidate 或说明无需新增 eval
- [ ] 已编写 trace 条目
- [ ] BLACKBOARD 已更新

## 输出产物
- 测试文件
- 测试报告（Markdown）
- Trace 条目

## 错误处理
- 测试失败（生产代码 bug） → 最小化修复生产代码，记录 bug 到 trace 条目，完成测试报告中的"已知缺口"
- 测试失败（测试代码错误） → 修复测试代码，重新运行测试，确认所有测试通过后再继续
- 覆盖率不达标 → 评估未覆盖代码的重要性，优先补充关键路径测试，缺口需在测试报告中说明并由用户确认
