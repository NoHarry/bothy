# 增强版代码评审工作流

本文档定义了 AI 代码评审的完整工作流程，包括评审提示模板、JSON 中间格式、确定性评分矩阵、质量自检清单、LSP 上下文收集指令和复杂度路由规则。

---

## A. 评审 Prompt 模板

### Role 定义

```
你是一名资深代码评审专家。
```

**重要**：Role 定义中禁止硬编码任何技术栈（如 Android、Java、Kotlin、MCP 等）。技术栈信息通过以下方式注入：

### 项目背景注入

```
从项目的 AGENTS.md（如存在）和被评审文件的语言/框架自动识别技术栈，作为评审背景。
评审前检查项目根目录 .review/rules/*.md，如存在则加载为项目特定规则，项目规则优先级高于通用评审标准。
```

### 评审范围（5 维度）

评审必须逐项检查以下 5 个维度，并对每个维度给出明确的检查结论：

| 维度 | 说明 | 示例问题 |
|------|------|----------|
| 缺陷 | 空指针、数组越界、资源泄漏、并发问题、逻辑错误 | `getString()` 返回 null 未判空 |
| 安全 | 硬编码密钥、SQL注入、XSS、权限校验缺失 | API密钥写在代码里 |
| 兼容 | API版本兼容、多设备适配、向后兼容 | 使用了 minSdk 26 的 API 但项目 minSdk 是 21 |
| 性能 | 主线程耗时操作、内存泄漏、冗余计算 | 在 UI 线程做网络请求 |
| 改进 | 可选的代码优化建议（不影响评分） | 建议抽取常量避免魔法数字 |

### 禁止输出的模式

评审输出中**严禁出现**以下模式：

- ❌ "代码结构清晰" / "逻辑合理" — 空洞夸奖，不提供任何信息
- ❌ "建议优化" / "可以考虑" — 无实质建议内容
- ❌ 不包含具体文件名和行号的评审意见
- ❌ 与原代码完全相同的"修改建议"

## B. JSON 中间格式模板

AI 必须首先输出结构化 JSON，然后从中提取最终评审意见。

### JSON 结构

```json
{
  "module": "模块名",
  "findings": [
    {
      "category": "缺陷|安全|兼容|性能|改进",
      "severity": "P0|P1|P2",
      "file": "文件名.java",
      "line": 42,
      "description": "具体问题描述",
      "suggestion": "具体修复建议",
      "rule_id": "R-XX（如匹配项目规则则填写，否则留空）",
      "deduction": -15
    }
  ],
  "score": 85,
  "score_breakdown": "100 - 15(缺陷x1) = 85",
  "verdict": "通过|不通过",
  "summary": "[缺陷]文件名:行号-问题描述"
}
```

### 字段说明

| 字段 | 说明 | 输出要求 |
|------|------|----------|
| `summary` | 评审意见摘要，格式为 `[标签]文件名:行号-问题描述` | 写入本次评审输出 / agent runtime / MR 描述，不写 CSV |
| `score` | 最终评分（0-100） | 与通过/不通过结论一起展示 |
| `verdict` | 通过或不通过 | 与评分一起展示 |

### 输出流程

1. AI 首先输出完整的 JSON 结构
2. 然后基于 JSON 中的 `findings` 数组生成可读的评审意见
3. 最终输出时只显示可读格式，JSON 仅作结构化存储用

## C. 确定性评分矩阵

### 评分起点

评分起始分数：**100 分**

### 扣分规则表

| 类别 | 严重级别 | 扣分 | 说明 |
|------|---------|------|------|
| 缺陷 | P0（空指针/资源泄漏/崩溃） | -20 | 直接导致运行时异常 |
| 缺陷 | P1（逻辑错误/边界条件） | -10 | 功能不正确但不崩溃 |
| 缺陷 | P2（潜在问题） | -5 | 特定条件下可能出问题 |
| 安全 | P0（硬编码密钥/敏感信息泄露） | -25 | 一票否决 |
| 安全 | P1（权限/校验缺失） | -15 | 存在安全隐患 |
| 兼容性 | P0（API 版本不兼容） | -20 | 平台/版本限制 |
| 兼容性 | P1（向后兼容风险） | -10 | 可能影响旧版本 |
| 性能 | P0（主线程阻塞/ANR 风险/死锁） | -20 | 直接影响用户体验 |
| 性能 | P1（内存泄漏/冗余计算） | -10 | 长期运行才暴露 |
| 改进 | — | 0 | 仅建议，不扣分 |

### 项目规则加权

当匹配到 `.review/rules/*.md` 中的项目规则时，使用规则自身的扣分值。

### 否决规则

**安全 P0 → 无论评分多少，直接判定为"不通过"**

### 计算公式

```
最终分数 = max(0, 100 - sum(通用扣分) - sum(项目规则扣分))
```

### 验证示例

#### 示例 1：lib_resource（通过）

- findings: P1 缺陷 (-10), 改进 (0)
- 计算: 100 - 10 - 0 = 90
- 结果: 90 ≥ 80，**通过** ✓

#### 示例 2：module_action（不通过）

- findings: P0 缺陷 (-20), P1 安全 (-15), P0 性能 (-20)
- 计算: 100 - 20 - 15 - 20 = 45
- 结果: 45 < 80，**不通过** ✗

## D. 评论质量自检清单

评审完成后，在输出最终意见前，逐条对照以下清单：

1. ☐ 每条意见是否包含具体文件名？（没有 → 删除该条意见）
2. ☐ 每条意见是否包含行号？（有 → 保留；无法确定 → 标注"行号未知"）
3. ☐ 每条意见的标签是否为 [缺陷]/[安全]/[兼容]/[性能]/[改进] 之一？（不是 → 修正标签）
4. ☐ 建议的修改是否与原代码不同？（相同 → 删除，说明建议无效）
5. ☐ 是否包含空洞夸奖？（如"代码结构清晰" → 删除）
6. ☐ 纯注释/文档改动是否检查了注释准确性？（否 → 补充检查）
7. ☐ 评分是否按矩阵计算而非主观感觉？（必须在 score_breakdown 字段中列出计算过程）

## E. 上下文收集指令（LSP 工具）

**适用范围**：深度评审模式

对于每个被修改的方法或类，按以下顺序执行 LSP 工具（best-effort）：

### 1. 获取定义信息

```
lsp_goto_definition
```

获取被修改方法所实现的接口或基类定义。

### 2. 查找调用者

```
lsp_find_references
```

查找被修改方法的调用者（最多展示 5 个）。

### 3. 获取符号列表

```
lsp_symbols(scope="document")
```

获取被修改文件的完整符号列表。

### 上下文注入

将收集到的上下文信息注入到评审 Prompt 的"相关上下文"部分。

### 重要说明

⚠️ **LSP 调用为 best-effort**。如果 LSP 不可用或超时，跳过此步骤，仅基于 diff 进行评审。

## F. 复杂度路由规则

在开始评审前，分析 diff 特征以确定评审深度。

### 路由表

| 条件 | 评审级别 | 行为 |
|------|---------|------|
| 仅注释/文档/空白行改动，且 ≤ 10 行 | 轻量评审 | 仅检查注释准确性，跳过 LSP，快速通过 |
| 改动行数 ≤ 200 且文件数 ≤ 5 | 标准评审 | 完整 5 维度评审 + 项目规则检查 |
| 改动行数 > 200 或文件数 > 5 | 深度评审 | 完整评审 + LSP 上下文收集 + 跨文件影响分析 |
| 包含二进制文件改动 | 跳过 | 二进制文件不评审 |

### 阈值常量（来自 config.sh）

| 常量 | 值 | 说明 |
|------|-----|------|
| `LIGHT_REVIEW_THRESHOLD` | 10 | ≤10 行改动 → 轻量评审 |
| `DEEP_REVIEW_THRESHOLD` | 200 | >200 行改动 → 深度评审 |
| `DEEP_REVIEW_FILE_THRESHOLD` | 5 | >5 个文件 → 深度评审 |
| `PASS_THRESHOLD` | 80 | 通过分数门槛 |

### 路由决策流程

```
1. 检查是否包含二进制文件
   └─ 是 → 跳过评审
   └─ 否 → 继续

2. 检查改动特征
   ├─ 仅注释/文档/空白行 且 行数 ≤ 10
   │   └─ 轻量评审
   ├─ 行数 ≤ 200 且 文件数 ≤ 5
   │   └─ 标准评审
   └─ 行数 > 200 或 文件数 > 5
       └─ 深度评审
```
